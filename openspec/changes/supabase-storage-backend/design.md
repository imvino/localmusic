# Design — Postgres (Supabase) storage backend

## Architecture

A third backend in `store.js` selected when `DATABASE_URL` is set. Postgres
drivers are async-only, but ~10 call sites in `server.js` rely on a
**synchronous** contract — rewriting them all to async is invasive and
pointless at household scale (~5 members, a few hundred KB).

Solution: **memory-hydrated adapter**. Postgres is the durable source of
truth; a hydrated in-memory copy serves the sync API; writes write-through
async.

**Hard precondition: exactly one live instance holds `DATABASE_URL`.**
Two instances = two diverging memory views, un-ordered writes, and
memory-derived retention deleting the other instance's rows. Documented
in `.env.example`; dev must never point at prod's Supabase.

## Backend selection

```js
const store = process.env.DATABASE_URL
  ? makePgBackend()      // init() is async; failure → sqlite with restored snapshot
  : makeSqliteBackend()  // → jsonBackend on native failure (unchanged)
```

`pgBackend.init()` is async — `server.listen` only runs after
`await store.init()`. sqlite/json get a no-op `init()` for a uniform call site.

## Connection (verified against Supabase + Render reality)

- **Session-mode pooler on port 5432** is the ONLY correct URL:
  direct `db.<ref>.supabase.co:5432` is IPv6-only and Render has no IPv6
  outbound; the 6543 pooler (transaction mode) rejects prepared statements
  which `postgres` issues by default.
- `sslmode=require`, `connect_timeout: 5`, `prepare` left at default true.
- Boot retry budget: 6 attempts, ~60s wall-clock (Supabase free-tier cold
  resume ~30s), backoff 5s→15s, env knob `PG_BOOT_RETRIES`.
- Never log the connection string — log host only.

## Write-through with LWW-safe retry

Each mutating accessor:
1. Mutates memory synchronously (identical semantics to sqlite backend).
2. Enqueues a pg write on ONE serialized promise chain per table.
3. **On failure: marks the entity dirty.** The retry task re-reads the
   row's *current in-memory state* at retry time — never replays the stale
   snapshot. If a newer write for the same key already succeeded, the
   retry is a no-op. This preserves last-write-wins end-to-end.
4. Retention (sweeps/caps) runs against memory and enqueues the same
   `DELETE ... NOT IN (SELECT ... LIMIT n)` statements sqlite uses — they
   execute against pg's truth, not a per-instance row list.

Dirty backlog is capped (10k ops) — beyond that, log ERROR per write
(memory still correct; the cap prevents unbounded growth during a
long pause).

## Durable-share exception

`createShare` / `deleteShare` / `getShare` return the queued write's
**settlement promise** — the routes `await` it before responding (they're
already async). A copied share link must never 404 because of a
write-through window; +30ms on a rare operation is free. sqlite/json
backends return a resolved promise for the same call shape.
`/s/:code` misses respond `Cache-Control: no-store` (a cached 404 today
persists 5 minutes past the row's existence).

## Pg-down fallback — serve the snapshot, reconcile on return

1. pg boot fails → if `data/app.db.imported` exists, copy it back to
   `data/app.db` (checkpointed snapshot = pre-cutover truth), THEN select
   sqlite. Members see their libraries, never an empty store.
2. Writes during the fallback window land in sqlite normally.
3. **Reconciliation:** on the next successful pg boot, import is per-row:
   for each sqlite row whose `ts` exceeds pg's `ts` (or pg row absent),
   upsert into pg. The "users table empty" gate is replaced by a per-row
   newest-wins merge — idempotent, fork-proof, and it heals fallback
   writes automatically.
4. After a clean pg boot, `app.db` is checkpointed (`wal_checkpoint
   (TRUNCATE)` — a WAL file is not a snapshot), then renamed to
   `app.db.imported` alongside any `-wal`/`-shm`. `.gitignore` gains
   `app.db.imported*` (the household DB must never reach git).

## Import transaction

Single pg transaction, `ON CONFLICT DO NOTHING`, all four tables;
failure → rollback → treat as unimported (retry next boot).
`play_events.id`: `BIGINT GENERATED BY DEFAULT AS IDENTITY` — imported
ids preserved by explicit insert, new ids continue past max.

## Observability

- `/api/health` reports `store.name` (`pg` / `sqlite` / `json`) — silent
  backend degradations become inspectable.
- Distinct ERROR lines: `pg connect failed (host h)`,
  `pg hydration failed`, `pg write dirty`, `pg write dropped (cap)`.

## What this deliberately does NOT do

- No Supabase SDK / Auth / Realtime — plain Postgres over a connection
  string; Clerk stays the auth authority.
- No client-side Supabase — Express remains the single authority.
- No cross-instance invalidation — single-instance precondition instead.
- No per-request async refactor — sync contract preserved.
